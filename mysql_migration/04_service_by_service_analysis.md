# Service execution paths and behavioral migration analysis

Locations below complement the per-function catalog in [11](11_source_evidence_catalog.md). Entry points are wired in each `internal/httpapi/router.go`, `cmd/server/main.go`, and worker command; sources are current working-tree files. A configured route/worker is not proof of deployed use.

## Data model: schema mutation, publication and display

Table HTTP handler → `TableService.Create` ([line 100](../backend/data-model-service/internal/service/table_service.go#L100)) validates/normalizes name and tenant activity, creates UUID metadata and default object_id/updated_at fields → `TransactionManager.Run` checks identity grant inside the transaction → repository insert, tenant `CREATE TABLE`, field metadata, object_id unique index, schema-change record and any queue work. Field/link/options/portable-model and tenant-schema-migration services use the same store/schema manager abstraction. `SchemaManager` receives the actual transaction, so PostgreSQL currently couples DDL and metadata rollback (PG-05).

The ingestion-contract triggers publish JSON for the affected table after metadata edits, with a UUID version only when payload changes. Publication locks that table's metadata, validates tenant consistency, gathers fields/enums and exposes two read views (PG-06). The SQL ingestion reader uses these contracts instead of assembling the entire model on every write. A MySQL DDL intent workflow must publish only after physical validation and must retain stale-cache invalidation behavior. It must cover create/add/archive/drop/index and interrupted reconciliation, not only additive fields.

Display endpoints bypass generic repositories through [display/store.go](../backend/data-model-service/internal/display/store.go). Save locks the model table and validates versions; reads resolve owner metadata, requested display fields and linked captions into a bounded SQL projection. Triggers validate JSON configuration, clean references to deleted/archived fields/links and bump versions. Replacing JSONB columns without these rules would leave invalid captions or leak archived fields. Index worker/reconcile commands use River and `to_regclass`; the latter checks existence rather than full index equivalence. Future recovery should inspect physical definition and treat drift explicitly.

## Ingestion: single/batch write and asynchronous intake

Ingestion handler → `IngestService.Ingest` ([75](../backend/ingestion-service/internal/service/ingest_service.go#L75)) → selected model reader → normalize/validate payload → transaction at line 112. With an idempotency key, lookup is scoped by tenant; matching request hash/response-kind returns stored response, mismatched payload/kind is rejected. Then `TenantDataWriter.UpsertRecord` writes the physical model table, `RecordIngestion` writes audit plus outbox via pgx Batch, and the idempotency response is inserted before commit. Validation-failure audit uses a separate best-effort transaction; the caller deliberately ignores its returned error. This is existing behavior, not a guarantee of complete failure auditing.

Exact upsert: sort field names → parameterized INSERT with UUID, lookup key, updated_at and provided fields → `ON CONFLICT (lookup_field) DO NOTHING RETURNING id` → on pgx.ErrNoRows call `patchRecord`, which updates provided fields and returns id. Patch mode tries update first and falls back to insert when absent. Default lookup is object_id, whose uniqueness is installed by data-model TableService. Unrelated unique field violations are errors, not permission to update a different record. The next-statement READ COMMITTED comment is an explicit visibility assumption. MySQL `INSERT IGNORE` can hide unrelated errors; generic ON DUPLICATE KEY UPDATE targets any unique conflict and cannot blindly preserve this contract (PG-08).

`BatchIngest` validates before entering its transaction at [294](../backend/ingestion-service/internal/service/ingest_service.go#L294), then loops record writes/audits/outbox and persists one batch response. It is not a COPY-based bulk path. Cancellation, duplicate object IDs, alternate unique-field conflicts and failure at the final audit/idempotency step must leave no partial successful batch. Concurrent identical idempotency keys are protected by the PK at insertion, but the initial read is not a reservation; test current loser/error behavior before promising replay success for simultaneous callers.

Upload/deferred creation → `UploadLogService.Create` / `DeferredIngestService.Create` → store row and River `EnqueueTx(store.RawTx())` when a transaction manager exists. Fallback paths and no-op enqueuer defaults remain in source; earlier historical refactors were reverted. Worker RunLog/RunDeferredIngest and retry handlers update attempt/status and reschedule work. Port these actual paths and explicitly define absent-queue failure behavior. Do not claim an ingestion outbox is delivered merely because a row is inserted.

Read APIs → `GetRecord/ListRecords/QueryRecords/AggregateRecords` → metadata-bound identifiers and parameterized dynamic SQL. Aggregations support count/sum/avg/min/max/count-distinct and boolean filter trees; supported pushdown subsets vary by configuration. Current list order is updated_at descending without an ID tie-break in those generic readers. Document tie behavior as a baseline gap rather than promise deterministic pagination that does not exist. Read-pool routing must preserve read-after-write needs and shared-database authorization.

## Decisions and detection

Decision route → `DecisionService.EvaluateScenario` / `evaluateScenario` ([366](../backend/decision-engine-service/internal/service/decision_service.go#L366)) → tenant/scenario/iteration/rule metadata and caches → AST trigger and rule evaluation → build workflow/screening/scoring work → transaction at [597](../backend/decision-engine-service/internal/service/decision_service.go#L597). That transaction persists decision and rule evidence, workflow executions, screening executions, scoring requests, outbox records, and River jobs. A rejected job insertion must roll back the corresponding business state. The transaction is downstream of evaluation; do not infer that all historical reads and persistence use one global snapshot.

AST runtime → aggregate compiler/read contract → ingestion HTTP by default in root Compose, or direct `postgres.TenantDataReader` in SQL mode. Both SQL implementations dynamically quote tenant tables; the direct adapter uses `to_jsonb(t)` for records. Preserve null handling, float/int aggregate results, time-window boundaries and AST fallback behavior. Caches/concurrency limiters are process mechanisms, not PostgreSQL features, but invalidation/version behavior depends on database contracts.

`DecisionRepository` exposes full reads, summary lists, offset and cursor pages, counts and filters. Cursor query at [228](../backend/decision-engine-service/internal/store/postgres/decision_repository.go#L228) uses descending created_at/id and UUID casts; search joins scenarios and ILIKE across text/UUID representations. Migrations 13–15 and 22 add tenant/time, outcome, object, prefix and score indexes. Preserve summary projections and avoid loading evidence/request JSON into queues. Current PostgreSQL plans are not evidence of MySQL performance.

Scenario publication, structured workflows, snoozes, custom lists, risk snapshots, tags and IP flags all have repository operations indexed in 11. `ListStructured` reads ordered condition/action JSON in one statement and rejects more than 500 rules; authoring transactions lock the scenario, replace children and append audit. MySQL JSON aggregation ordering must not reorder action execution. Async/scheduled workers, callbacks and dispatch each have status/retry/idempotency state in SQL and separate queue policies. Their uniqueness and recurrence keys must survive replacement, not just their payloads.

Screening authoring/read paths in the working tree add owner audit and identity checks. Decision-side execution projection is maintained by a core-owned SQL function called from screening; it validates source/decision/config/scenario binding, rejects ambiguity and advances only newer source versions. HTTP callbacks are supplementary and cannot replace this durable repair path without an explicit design.

## Screening: provider matching, fencing, review and history

CreateScreening/manual/scenario/continuous intake → transactionally persist screening and enqueue River job. Candidate generation occurs in the HTTP provider (`internal/clients/provider`), not in a PostgreSQL similarity query. Worker `DispatchService.RunScreening` → atomic `Claim` → provider Search outside DB transaction → result conversion → transaction: `LockClaim` validates token, read exclusions for continuous scope, `ReplaceForScreening` deletes/reinserts candidates, record exclusion applications, update screening, enqueue requires-review event when appropriate ([dispatch_service.go:159](../backend/screening-service/internal/service/dispatch_service.go#L159)). An incomplete provider response remains awaiting_review even with zero matches; it must not become a negative result.

The claim uses a new UUID token and six-minute lease. A later claimant supersedes the token; the old worker fails before publishing candidates. `ReplaceForScreening` itself accepts only screening ID and trusts its caller's authorized parent/claim context—retain that contract or strengthen it deliberately, not by assumption. Failure release is token-conditional with cancellation-independent cleanup. Recovery lists expired processing identities with a bounded limit, then rechecks current rows. Tests must prove a live claim cannot hide expired work behind a scan limit and a stale worker cannot replace reviewed evidence.

Case events are inserted with screening result/review/file changes. Delivery worker claims one pending/expired event with SKIP LOCKED, advances attempts and lease, sends HTTP, then finishes only if the attempt still matches. Case intake uses stable event identity and receipt hashes. Execution projection has a distinct queue: source row → queue row → savepoint/core owner contract → version-conditional queue delete. Projection failures roll back the savepoint and retain retry/error state. These two delivery mechanisms serve different atomicity boundaries (PG-14/15).

Manual search creator identity is encoded in `manual:<actor>:...` idempotency keys; history reads require tenant, actor and manual-origin predicates, use created_at/id keyset pagination and JSON name extraction. Manual case creation rechecks source and candidate eligibility under locks. Keep actor identity from trusted auth, never from arbitrary request parameters. The manual history expression index and exclusion-history indexes are recent migrations; include them in target schema/performance tests.

Investigator review → shared investigator.Run → screening owner apply function. Continuous dismissal can upsert an exclusion, write exclusion event, change match/parent state, then the shared code writes investigator_reviews and case event/outbox. The current deferred FKs permit this child-before-parent ordering; the future implementation must precompute/insert the validated review parent, then exclusion event, then current exclusion, within the same transaction, while preserving expected-version checks and immutable history. This is a proposed design requiring tests, not a verified direct port. Parallel-array `unnest` application writes require batch-row correspondence tests.

## Cases and investigation

Case routes → lifecycle/intake/bulk/manual services → `UnitOfWork.WithinTransaction` → current identity recheck/locks → case/inbox/resource locks → owner repositories → events/outbox → commit. [transactions.go:36](../backend/case-manager-service/internal/store/postgres/transactions.go#L36) releases locks on cancellation using a separate cleanup context. Decision membership transfer updates link ownership and associated screening links atomically; source audit/files remain. Do not turn the migration into deletion/recreation of cases or history.

Reliable intake locks tenant/scope/key before receipt lookup, verifies payload hash, resolves/creates case and links, then records receipt. Automatic assignment uses bounded work, locks one eligible case and member, and the assignment trigger provides the final capacity guard shared with human assignment/reopen/move. Archiving/inbox permissions and status constraints remain independent of SQL storage choice. Tenant-composite FKs prevent a parent from another tenant; application identity and inbox access are additional requirements.

Workspace, decision selection and explorer queries read other owners directly with tenant and access predicates. Explorer follows registered links/pivots and projects only published fields, rejecting an oversized displayed record; avoid replacing it with arbitrary scans or per-row network calls. Queue/detail separation and keyset sorts must be retained.

Reports persist JSON content and lifecycle/version metadata; evidence uploads persist BYTEA plus digest/finalization/expiry and are cleaned in bounded locked batches. Analytics uses one statement snapshot for permissions, cohort and event-derived aggregates; MATERIALIZED CTEs/FILTER/GROUPING SETS and ordered JSON require explicit rewrites. Its 1,001-group sentinel causes an error above 1,000 inbox/assignment groups; target code must not silently truncate. AI review tables/jobs do not prove an external AI implementation is deployed; retain current status/error contract.

Case maintenance is scheduled through River in `case_queue`; outbox delivery remains durable case state with leases and stable IDs. Neither missing publisher configuration nor successful queue initialization demonstrates successful external delivery.

## Authentication and authorization

OIDC HTTP login authenticates an external issuer/subject; app `platform.Store` resolves/creates a local user, membership and session. Login transaction nonce/verifier/binding digests, session digest/expiry/idle/revocation, membership roles/version, invitations and audit are in `identity`, not delegated to Keycloak. Role updates serialize tenant-admin decisions to prevent concurrent removal of the last administrator. Invitation acceptance locks issuer/subject and invitation state; delivery has generation/lease fencing. Session and role mutations must continue to conflict with authorized business writes.

`identity.authorize_case_v1` and `authorize_data_model_v1` validate current user/member/session/tenant and expected authorization version. Mutation calls acquire user→membership→session shared locks before domain locks. Merely verifying a JWT is not equivalent. Shared investigator and case/data-model services depend on these SQL functions. MySQL replacements must preserve both fail-closed reads and revocation-versus-write linearization.

Optional Keycloak keeps provider realm/credential state in its own PostgreSQL schema. Its database conversion is provider-managed and must preserve issuer/subject mappings into application identity. Export/import coverage, sessions, credentials and provider version support are open questions. External production IdPs may not use the local profile at all.

The identity-preflight CLI is a separate SQL consumer: [ReadPage](../backend/auth-service/internal/preflight/inventory.go#L113) explicitly uses a read-only REPEATABLE READ transaction, local statement/lock/idle timeouts and a tenant registry timestamp, then keyset-pages owner identity references. Pages from separate calls do not share a snapshot. Preserve those limits and do not use its paginated output as a migration-grade census without fencing writers or a shared snapshot. This is a concrete exception to the common default transaction options elsewhere (PG-12/23/27).
