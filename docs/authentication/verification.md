## Real process acceptance

Fresh API binaries were built locally and exercised with temporary keys and disposable PostgreSQL databases:

1. **Interactive session → queue → review → replay → logout:** auth-service resolves a real persisted opaque session through signed BFF bootstrap transport, Case Manager returns the queue, and the decision owner commits/replays a case review. Logout immediately prevents protected review replay; an already-issued ordinary read snapshot remains valid until expiry. This starts from a provisioned OIDC identity/session. The external identity provider's live login UI was not deployed; its protocol is covered by the auth-service fixtures.
2. **External proof → one system token → ingestion and decisions:** a client signs a 60-second proof and exchanges it at the real auth HTTP handler for one 15-minute `urn:fraud:system` access token carrying `ingest:write`, `decisions:evaluate`, and `decisions:read`. The exact same token submits a transaction to the actual ingestion process, requests a decision from the actual decision process, and reads decisions. The decision process retrieves its model from the actual Data Model API with a separately signed internal credential. SQL assertions verify ingestion and decision persistence. Cross-tenant requests, human-only authoring, a decision read with an ingestion-only token, and assertion replay are rejected. All migrations, including River queue migrations, run only against disposable test databases.
3. **Outbox → Case Manager → lost acknowledgement → retry:** the real polling/delivery component reads a durable screening outbox row and calls the actual Case Manager process. A proxy loses the first successful acknowledgement; retry sends a newly signed token, preserves tenant/originator identity and produces one receipt/case effect.
4. **Migrated existing process journeys:** continuous producer-to-case delivery, execution callback projection/recovery and both investigator owner review journeys pass. Scenario authoring/evaluation passes, including revoked-session mutation denial and snapshot reads. Actual decision and screening worker processes also pass provider retry/failure/timeout, case delivery, address/birth/name handling and API/worker configuration-drift scenarios. Third-party provider HTTP is synthetic in these journeys; application processes, queues and database persistence are real.

Legacy optional screening process harnesses now use typed human/service credentials and separate private leaves. The controlled-watchlist/restore/performance journeys have not all been rerun; their normalizer prerequisite is currently failing as described below. This is not evidence of acceptance for those feature suites.
