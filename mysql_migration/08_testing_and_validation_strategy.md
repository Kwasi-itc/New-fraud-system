# Testing and validation strategy

No application tests or databases were run for this documentation phase. Listed suites are reusable evidence targets, not reported passes. Some real-DB suites skip without a test URL; future CI must distinguish passed, failed and skipped tests and require the database suites for migration acceptance.

## Test environment and baseline

Use explicitly labeled disposable PostgreSQL and MySQL databases, applying all real service migrations in dependency order. Never point destructive fixtures at `fraud` or reuse application credentials. Guard database/container identity before DROP/TRUNCATE. Freeze the source snapshot and report engine/driver versions, timezone, collation, SQL mode, isolation, pool limits, hardware and dataset. Run PostgreSQL behavioral baselines before target comparisons; mocks only verify contracts, not SQL locking or optimizer behavior.

The source inventory contains unit query-builder tests, real PostgreSQL integration tests, Python HTTP contracts, frontend Playwright tests and workload/plan tooling. Keep HTTP/domain assertions, replace driver/setup/query assertions only where engine behavior legitimately differs. Test both direct SQL and configured HTTP read paths. Include worker, migrate, reconcile/admin and delivery executables, not just server binaries.

## Required concurrency schedules

Use deterministic barriers rather than sleep-only tests. Run at least: (1) both ingestion requests read absent idempotency, then both write; (2) worker A claims, expires, B completes, then A publishes; (3) role revocation waits behind an authorized mutation and then blocks the next write; (4) two last-admin removals; (5) two assignments at the last capacity slot; (6) schema changes on same versus different tables; (7) source update locks source then queue while projector attempts both; (8) same candidate review versus exclusion removal/replacement; (9) same decision attached/transferred concurrently; (10) commit success with lost client response followed by retry. Assert resulting rows/events/jobs, external calls, error types and released locks. Repeat under the chosen target isolation and pool exhaustion/cancellation.

## Performance and operational acceptance

Reuse workload shapes from `backend/stress-tests/decision_rule_complexity_scaling.py`, scenario-scaling scripts, `production_replay`, `system_tests`, plus source plan tests such as `TestContractLookupPlanAtRepresentativeMetadataSize`, display plans and decision-selection plans. Existing reports are not a controlled cross-engine comparison.

Construct datasets from measured production-like tenant count/skew, dynamic table/field count, historical decision/case depth, pending-versus-completed queue ratio, blob/JSON size, object cardinality and filter selectivity. Run cold/warm cache, sync/async decisions, burst ingestion, schema edits under load, many queue consumers and slow external providers. Keep hardware and durability requirements comparable; do not trade persistence guarantees for throughput silently.

Capture p50/p95/p99 request latency, throughput, error/retry rates, pool wait/occupancy, queue age/drain rate, lock/deadlock/timeouts, CPU/I/O, rows examined, memory/temp spill and replication lag where applicable. Compare PostgreSQL EXPLAIN ANALYZE/BUFFERS with MySQL plan/actual execution metrics. Pay special attention to case analytics, selective decision filters, identity checks, manual history actor key, exclusion scope lookup and lease claims. Full scans may be legitimate for a bounded analytic cohort but require measured resource cost. Do not assert an optimization from index presence alone.

Numeric performance gates are intentionally unresolved until Q-01/M-01 sets them. Acceptance requires no unexplained correctness difference, no tenant/auth breach, no missing durable work/audit, bounded resource behavior, signed-off performance thresholds and rehearsed restore/cutover. Passing a small fixed-schema prototype is insufficient.
