# Implementation audit

Status: Stage A static inspection complete; runtime verification remains pending. Source identity and scope are in [README](README.md). Paths below are relative links from this directory. Symbol names are included because the working tree is changing and line numbers can drift.

## Request and decision path

1. [router.go](../../decision-engine-service/internal/httpapi/router.go) registers `POST /v1/tenants/:tenantId/scenarios/:scenarioId/evaluate`, `POST /v1/tenants/:tenantId/decisions`, and `POST /v1/tenants/:tenantId/decisions/all`. [DecisionHandler](../../decision-engine-service/internal/httpapi/handlers/decisions.go) binds the payload and selects synchronous or deferred execution from live mode, object-type overrides and admission settings. The deferred helpers reject with `429 live_decision_overloaded` when async fallback is disabled. A `202` with an async execution is acceptance, not a completed decision.
2. [prepareObject / DecisionService.prepare](../../decision-engine-service/internal/service/object_preparation.go) resolves the tenant model, trims object identity/type, rejects unknown or archived object types, and validates the full object. Empty or omitted `fields` loads the stored object through `TenantDataReader.GetRecord`; it is not an empty-payload evaluation. Inline fields do not automatically ingest the transaction.
3. [payload.Validator.Validate](../../decision-engine-service/internal/domain/payload/validation.go) checks identity, every supplied field, required fields, nullability, type and enum membership. Missing nullable fields become null. Nonnullable omissions fail. Numeric strings and boolean strings have explicitly implemented normalization; malformed values do not silently become a rule miss. Compiled schemas are tenant/type/revision keyed, bounded to 128 entries and have a 30-second TTL.
4. [EvaluateAllLiveScenarios](../../decision-engine-service/internal/service/decision_service.go) prepares once, selects live scenarios for the tenant and object type, and runs bounded scenario goroutines. [ScenarioRepository.ListLiveByTriggerObject](../../decision-engine-service/internal/store/postgres/scenario_repository.go) queries `core.scenarios` with tenant, trigger-object and non-null live-iteration predicates, ordered by creation time descending. There is no priority-based global decision reduction. No applicable scenarios yields an empty result array after payload validation.
5. `DecisionService.evaluateScenario` loads scenario and live iteration; checks object type; evaluates the trigger first. A false trigger returns `triggered:false`, no decision and no rule executions. A true trigger loads all iteration rules and active object snoozes.
6. [evaluateRules](../../decision-engine-service/internal/service/rule_evaluation.go) evaluates every unsnoozed rule through `EvaluateFormulaWithEvidence` using an errgroup. A hit does not stop subsequent rules. Results retain rule-list order. Default rule concurrency is min(8, GOMAXPROCS, rule count); default scenario concurrency is min(4, GOMAXPROCS, scenario count). Explicit configuration overrides these defaults, with configuration caps of 64 and 32 respectively. These are concurrency limits, not rule/scenario count limits.
7. Matching rules add their integer `ScoreModifier`; snoozed rules contribute nothing and get `snoozed` executions. Other executions are `hit` or `no_hit`, with evidence. [outcomeFromScore](../../decision-engine-service/internal/service/evaluator.go) uses inclusive thresholds in order: decline, block_and_review, review, otherwise approve. Thresholds must be ordered review <= block_and_review <= decline. Equal thresholds therefore favor the more severe outcome.
8. Workflow, screening and scoring work is constructed before persistence. A transaction inserts the decision, rule executions, work records, outbox events and transactional River jobs. Return occurs after commit. [RuleExecutionRepository.CreateMany](../../decision-engine-service/internal/store/postgres/rule_execution_repository.go) currently performs one `INSERT ... RETURNING` per rule and serializes/deserializes evidence for each; its name does not imply a single batched SQL statement.
9. Network delivery and worker execution happen separately. [ExecutionService](../../decision-engine-service/internal/service/execution_service.go) handles async/scheduled execution, retry state and callbacks; [async worker](../../decision-engine-service/internal/riverjobs/async_execution_worker.go) invokes it. Async execution uses the decision service and validates at execution time. Screening/scoring completion is not part of synchronous decision response latency; optional screening name recognition during work construction can add a synchronous dependency when configured.

## Failure and consistency semantics

- Invalid JSON is a request failure; model-invalid inline objects are normally HTTP 422. Invalid stored objects are classified as HTTP 500. [evalerrors.Classify](../../decision-engine-service/internal/evalerrors/classify.go) distinguishes unsupported aggregate/broad-read errors (422), remote dependency errors (502), wrapped ingestion overload (429), and internal errors. Some classification depends on error strings; assert category/status for specific faults rather than assuming all timeouts share one status.
- Trigger/rule evaluation errors abort that scenario before persistence. The rule errgroup cancels siblings; cancellation suppression preserves the original non-cancellation error. Persistence failure rolls back that scenario's transaction. No automatic approve-on-error behavior was found in this path.
- Multi-scenario requests have **one transaction per triggered scenario**, not a transaction covering the whole request. One scenario may commit before another fails and the endpoint returns an error. A blind retry can write further decisions. Explicit async idempotency is not proof of exactly-once synchronous decisions or atomic all-scenario processing.
- Aggregate and reference reads occur before the decision write transaction. They do not share a single database snapshot across all queries. Concurrent ingestion can legitimately change results between requests, and between distinct reads in one evaluation. Cached identical reads may reuse their first value within that request.
- `TimeNow` is captured once for a multi-scenario evaluation. Decision timestamps/IDs and stored history still change between executions. Compare semantic outcomes separately from generated identity/time fields.

## Representation, authoring and execution strategy

[Scenario / Iteration / Rule](../../decision-engine-service/internal/domain/scenario/model.go) hold a scenario trigger object and live iteration pointer; iteration trigger JSON, thresholds, status and optional schedule; and rule formula JSON, score modifier, display order, group, snooze group and stable ID. Rules are JSON ASTs, not SQL snippets or a separate rules-engine service. [ast.Node](../../decision-engine-service/internal/domain/ast/model.go) supports `function` and compatibility `name` forms, constants, children and named children.

[RuleService.Create/Update](../../decision-engine-service/internal/service/rule_service.go) enforces draft ownership and basic rule validation; creation alone is not full formula validation. [ValidationService.ValidateIteration](../../decision-engine-service/internal/service/validation_service.go) parses triggers/rules, invokes `ValidateNode`, requires boolean formula results and checks thresholds. [IterationService.Commit](../../decision-engine-service/internal/service/iteration_service.go) calls validation; [PublicationService.Publish](../../decision-engine-service/internal/service/publication_service.go) requires a committed iteration and checks data-model/index preparation. Benchmark setup must wait for required index jobs and verify publication, not just successful rule creation.

[EvaluateFormula](../../decision-engine-service/internal/runtime/ast_eval/evaluator.go) and [EvaluateFormulaWithEvidence](../../decision-engine-service/internal/runtime/ast_eval/evidence.go) unmarshal AST JSON and interpret nodes at evaluation time. There is no general compiled execution plan or cost-based rule ordering in this path. AND/OR short-circuit within an AST; evidence records skipped branches. Evidence traversal also visits child nodes and invokes evaluation, with memoization reducing repeated computation. This makes bare-node microbenchmarks different from production evidence-producing evaluation.

Metadata caches in `decision_service.go` use tenant-aware keys, a 30-second TTL and singleflight loads. Mutation services invalidate their attached in-process caches. No cross-replica invalidation mechanism was established by this audit. [EvaluationCache](../../decision-engine-service/internal/runtime/ast_eval/evaluation_cache.go) is request scoped, singleflights nodes and caches successful results. Its key JSON-serializes tenant, object identity/type, the entire field map, captured time and node, then hex-encodes the bytes. Identical rules and large payloads must therefore be separate experiments. [AggregateResultCache](../../decision-engine-service/internal/runtime/ast_eval/aggregate_result_cache.go) shares equivalent aggregate queries within a request. Related paths and GeoIP have additional evaluation caches. There is no demonstrated cross-request cache of final fraud decisions.

## Historical data and database dependencies

[tenantdata reader factory](../../decision-engine-service/internal/tenantdata) selects `ingestion_http` or `direct_db`. The [HTTP client](../../decision-engine-service/internal/clients/ingestion/http_client.go) calls ingestion read APIs; the [direct reader](../../decision-engine-service/internal/store/postgres/tenant_data_reader.go) uses the decision database pool and model-resolved `tenant_<uuid>` tables. The [ingestion reader](../../ingestion-service/internal/store/postgres/tenant_data_reader.go) implements corresponding SQL. Both modes belong to the same logical PostgreSQL database architecture; HTTP is an implementation choice, not a requirement imposed by ownership.

`CompileAggregateQuery` compiles supported Aggregator nodes and nested filter groups into a parameterized query contract. Readers validate model fields and quote identifiers. COUNT counts non-null values of the selected field; COUNT_DISTINCT excludes null; SUM is coalesced to zero; AVG/MIN/MAX can return null for no qualifying values. Time windows are explicit filter predicates. There is no implicit current-payload inclusion, time bound, object-ID exclusion or universal historical-version filter in the inspected aggregate SQL.

`TraverseRelatedPath` follows declared `LinksToSingle` relationships, querying the parent field with limit 1 per hop. Path length, repeated paths and parent lookup indexes affect cost. `past_decision_count` retrieves `DecisionRepo.ListByObject` and counts/filter outcomes in Go: it is not a database COUNT or time-window query, and can grow with that object's complete decision history.

[Initial migrations](../../decision-engine-service/internal/migrations/metadata/000001_init.up.sql) establish `core` decision-owned tables and indexes for tenant/scenario, iteration rules, decision executions and platform lookups. Later migrations add decision filters, object-prefix and metric indexes. Foreign keys in the initial schema are often ID-only; tenant-aware repository predicates must not be confused with universal composite-FK enforcement. Dynamic history indexes depend on data-model preparation. Capture actual catalog/index definitions and plans; migration presence does not prove index use or tenant-consistent relationships in every deployed schema.

[docker-compose.yml](../../../docker-compose.yml) currently uses one `fraud` database. The decision API and worker explicitly allow count,sum,avg,count_distinct, while [application defaults](../../decision-engine-service/internal/app/config.go) allow count only. min/max need an approved runtime allow-list change for those deployment profiles. No running configuration was read or inferred from local defaults.

## Authorization

[authMiddleware](../../decision-engine-service/internal/httpapi/auth.go) on legacy v1 APIs implements disabled or shared bearer-token authentication. The decision evaluate routes do not establish per-user tenant membership/inbox authorization merely from the tenant URL. New private workflow/screening routes have separate boundaries. Baselines must retain the intended deployment auth boundary and test wrong tenant/resource combinations, invalid credentials and upstream user authorization separately. Service-token access is a trusted internal contract, not evidence of end-user authorization.

## What can be measured now

`GET /v1/admin/runtime-metrics` exposes process-level preparation, payload schemas, metadata cache, pgx pool, aggregate demand/cache/limiter, tenant reads and evaluation counters. [evaluation_metrics.go](../../decision-engine-service/internal/service/evaluation_metrics.go) uses only the last 512 samples for percentiles; these are not whole-run latency distributions. Multi-scenario `Triggered` records a nonempty result list, which is not the number of matching triggers. Fan-out calls the internal evaluator, so public single-scenario counters must not be read as a count of all child evaluations.

`logDecisionEvaluationTimings` logs debug phase durations, including rules, transaction inserts and commit. Scenario timing starts after preparation; client latency additionally includes preparation, auth, transport and serialization. `rules_eval_us` is wall time for a concurrent batch, not the sum of individual rule CPU times. Cache and pool deltas sampled inside concurrent requests overlap other traffic. Use isolated process-level counter deltas and separate diagnostic logging runs.

Likely costs, **not measured bottlenecks**: per-rule inserts/evidence size; AST decoding and payload-heavy cache keys; aggregate scan selectivity/indexes; per-hop relationship reads; whole-object decision history; HTTP/model lookups; nested scenario/rule concurrency and shared pool pressure. The plan collects evidence before proposing production changes.
