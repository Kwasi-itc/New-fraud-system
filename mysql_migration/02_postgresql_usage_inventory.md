# Consolidated PostgreSQL usage inventory

IDs identify behavioral dependency families; every discovered source occurrence is indexed by those IDs in [11](11_source_evidence_catalog.md), with function context and line links. [12](12_schema_source_catalog.md) retains full SQL definitions, including later alterations. The catalog is deliberately broader than confirmed PostgreSQL-specific usage: comments, standard SQL and tests are labeled and must not inflate the migration scope.

Classification: **P** explicitly PostgreSQL-specific; **B** both engines with potentially different behavior; **A** library abstraction (not proof of portability); **I** indirect dependency; **U** unresolved without runtime/provider inspection. Compatibility treatments C-01–C-15 are in [05](05_postgresql_to_mysql_compatibility.md); tasks M-01–M-16 are in [09](09_migration_roadmap_and_checklist.md).

## Classification limits and false positives

`github.com/gin-gonic/gin` and `GIN_MODE` are HTTP framework settings, not GIN indexes. Go `uuid` usage alone is portable; SQL UUID storage/casts are the dependency. `LIKE`, normal B-tree indexes, transactions, checks, CTEs and aggregation exist in both engines; their surrounding syntax and semantics determine work. The workflow snapshot comment mentions lateral aggregates but the inspected query uses correlated subqueries. No application `DISTINCT ON`, extension installation, GIN/GiST/BRIN or RLS creation was established; the source catalog's searches are not a live catalog assertion.

The generic family IDs also cover operational/test-only occurrences. River-generated sequences/enums/indexes and Keycloak schema details require dependency/live-schema capture (M-01); they are not fabricated from the application's hand-written migrations. Detailed per-function source entries should be used when estimating or implementing a family, not the headline family count.
