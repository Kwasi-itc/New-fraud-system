   Codebase Summary: Fraud Detection System 

  This repository contains an enterprise multi-tenant fraud detection, transaction ingestion, rule decisioning, sanctions/AML screening, and case management platform.
  ──────
  ## 1. High-Level Architecture & Shared Database Model

  The system follows a modular microservice architecture backed by a single logical PostgreSQL database (fraud). Schema ownership is strictly bounded by service:

  • identity: Owned by auth-service (users, memberships, tenant roles, sessions, audit).
  • core & dynamic tenant schemas: Owned by data-model-service (data models, physical tenant DDL tables, published ingestion contracts).
  • screening: Owned by screening-service (screenings, match reviews, exclusions, case event outbox).
  • case_manager: Owned by case-manager-service (inboxes, cases, assignment, investigation history, native evidence).
  • keycloak: Identity provider schema for OIDC federated authentication.

  Cross-service data access uses SQL read views (such as core.ingestion_contracts_v1) or explicit API/outbox contracts, ensuring narrow lock scopes, tenant isolation, and atomic transactional boundaries.
  ──────
  ## 2. Backend Microservices (Go)

  All core backend services are implemented in Go:

   Service                                   │ Path                                      │ Key Responsibilities
  ───────────────────────────────────────────┼───────────────────────────────────────────┼──────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────
   Data Model Service                        │ data-model-service                        │ Manages logical metadata, provisions per-tenant PostgreSQL schemas/tables, publishes schema validation contracts, manages pivots/links, and handles async secondary index jobs.
   Ingestion Service                         │ ingestion-service                         │ Ingests real-time events and batch CSVs, validates payloads against cached table contracts, executes atomic upserts into tenant schemas, and emits durable outbox events.
   Decision Engine Service                   │ decision-engine-service                   │ Scenario/rule authoring, AST evaluation, rule snoozes, scheduled batch execution, phantom/test runs, IP geolocation (DB-IP MMDB), decision persistence, and post-decision workflow triggers.
   Screening Service                         │ screening-service                         │ Sanctions, PEP, and AML screening intake, match review lifecycle (confirmed_hit / no_hit), exclusions/whitelists, and durable case callback delivery.
   Case Manager Service                      │ case-manager-service                      │ Investigation queues, inboxes, assignment lifecycle, case-decision links, evidence file uploads, contributor tracking, and strict role-based access.
   Auth Service                              │ auth-service                              │ OIDC/Keycloak integration, operator accounts, tenant memberships/roles, user invitations, opaque browser session management, and JWT claims issuance.
   Investigator Module                       │ investigator                              │ Shared Go library handling human JWT verification, session validation (identity.authorize_case_v1), and atomic case review transactions across services.
  ──────
  ## 3. Frontend Application (Next.js & TypeScript)

  Located in frontend/, the web interface is built with Next.js 16, React 19, Tailwind CSS v4, TanStack Query, and Zustand:

  • Detection Workspace: Interactive rule builders (simple, advanced, and expression-based), scenario management, test runs, and decision histories.
  • Cases & Investigation: Queue navigation, inbox administration, case assignment, structured record explorers, evidence uploads, and investigator review workflows.
  • Screening & AML: Freeform search, search history, stored screening evidence, and match reports.
  • Data Model Management: Visual schema editor, table and field configurations, and display settings.
  • Administration & Access: Platform invitations, user membership/roles, active sessions, and audit logging.
  • Secure Server Proxies: Server-side Next.js route handlers (/api/cases, /api/decisions, /api/data-model, etc.) that translate opaque browser session cookies into signed, short-lived JWTs forwarded privately to backend APIs.
  ──────
  ## 4. Orchestration, Gateway & Deployment

  • Local Stack Orchestration: docker-compose.yml starts Postgres, Keycloak, migration runners, backend services, background workers, and the frontend.
  • Single-Origin Gateway: docker/POSTGRES_GATEWAY.md and docker-compose.gateway.yml deploy an Nginx reverse proxy providing single-origin routing for frontend and API endpoints.
  • EC2 / Production Deployment: deploy/ec2/README.md provides automated EC2 provisioning, Caddy reverse-proxy with automated HTTPS, RDS configuration, and environment bootstrapping.
  • Migration Pipeline: Services migrate in strict sequential order upon startup: auth → data-model → ingestion → decision-engine → screening → case-manager.
  ──────
  ## 5. Testing & Performance Verification

  • Stress Testing & Simulation: stress-tests contains Python and k6 scripts for throughput benchmarking, production transaction replay, rule complexity scaling, and database resource sensitivity tests.
  • Integration Tests: Disposable PostgreSQL-backed integration test suites exist in integration-tests and within each individual service.
  • End-to-End UI Testing: Playwright browser test fixtures in frontend/tests and ui_test.

  The core problem involves high-stakes decision-making within a cluster, such as in financial transactions, where incorrect choices lead to significant financial or regulatory consequences. This differs from simpler actions due to strict regulatory compliance and the critical need
  for a tamper-proof audit trail of every decision. A major risk arises from potential race conditions where simultaneous actions on the same data could lead to inconsistent or erroneous outcomes.
  
  
  The core challenge centers on preventing double execution and ensuring data integrity during high-stakes actions within the cluster. The current implementation uses a multi-layered locking mechanism involving identity verification, advisory locks, case row locks, and input
  fingerprinting. These locks are designed to guarantee that operations are atomic and idempotent, mitigating the risks of race conditions. Verification of the user, team assignment, and cryptographic fingerprinting adds further layers of protection.
  
  
  The system prevents double execution by recognizing that a prior action succeeded via network timeout, issuing a confirmed receipt. Preserving the machine outcome, a human review is recorded alongside, creating an auditable history.
  
  The current implementation of the safety and locking mechanism is hardcoded, reaching directly into database tables within a specific library, which led to duplication across multiple code files. The aim is to create a standardized tool for high-stakes, regulatory actions.

  ### The Big Picture: What is Cluster C Really Doing?

  Think of your fraud system as having two completely different types of actions:

  1. Everyday Actions (Low Risk):
      • A user views a dashboard, searches for a customer, or browses a list of transactions.
      • If two people view a dashboard at the same second, nothing breaks. If a network packet drops, you just refresh.
  2. High-Stakes Investigation Actions (High Risk & Legal/Regulatory):
      • An investigator clicks "Approve $50,000 Wire Transfer" or "Decline & Freeze Account".
      • An investigator marks a person as a "Confirmed Sanctions Hit (Terrorist / Sanctioned Entity)" or "False Positive".


  Cluster C is dedicated entirely to how the system protects those high-stakes, irreversible actions.
  ──────
  ### The 3 Real-World Nightmares Cluster C Prevents

  To understand why Cluster C exists, consider what would happen without it:

  #### 1. The "Two Investigators at Once" Nightmare (Race Conditions)

  • The Scenario: Alice and Bob are two fraud analysts who have the same case open on their screens at 9:00 AM.
      • At 9:01:00 AM, Alice clicks "Decline & Freeze Money".
      • At 9:01:00 AM (exact same millisecond), Bob clicks "Approve & Release Money".
  • Without Cluster C: The computer might send the money out AND freeze the account, or save conflicting records where Alice thinks it was blocked, but the bank actually paid out.
  • With Cluster C: The instant Alice clicks, the database puts a digital padlock on that specific case row. Bob's computer is forced to wait in line. Once Alice's action commits, Bob's screen updates: "Case already decided by Alice; refresh to view."

  #### 2. The "Double-Click & Bad Wi-Fi" Nightmare (Replay Attacks & Retries)

  • The Scenario: Alice clicks "Approve". Her office Wi-Fi blips for 2 seconds. The browser button spins. Impatiently, Alice clicks "Approve" two more times.
  • Without Cluster C: The system might try to execute the approval multiple times, duplicate audit records, or corrupt the state.
  • With Cluster C: The system creates a cryptographic fingerprint (a SHA-256 hash) of Alice’s exact action and notes. When the second click arrives, the database recognizes: "I have already committed this exact action! Here is Alice's existing confirmed receipt." It guarantees
  that clicking 1 time or 10 times produces the exact same result once.

  #### 3. The "Auditor & Regulatory" Requirement (Immutability)

  • Financial regulators require proof that human actions cannot alter history.
  • If the AI decision engine calculated: machine_outcome: "block_and_review", that machine decision can never be erased or rewritten.
  • Alice's human decision (human_status: "approved", findings: "Called customer to verify passport") is stored alongside the machine outcome as an immutable, permanent legal record.

  ### Why We Need to Standardize This (The Problem Today)

  The mechanism itself works well, but here is the architectural flaw:

  1. It Reaches Into Foreign Tables Directly:

  • Clean Interface: Instead of services running raw SQL queries against case_manager tables, the Case Manager provides a clean database function:

  • Generic Pipeline in Shared Module: We package this locking, idempotency-hash, and audit pipeline into our shared Go module.
  • Future Proofing: Whenever any team builds a new high-stakes feature (e.g., AML regulatory report filing, customer chargeback disputes), they don't invent new locks or copy-paste SQL. They simply plug into this standard pipeline.
